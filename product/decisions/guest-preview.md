# 访客预览（Guest Preview）— 产品决策稿

Written 2026-08-29. 依据 owner 于 2026-08-29 的要求新增，经 Codex 产品评审。
**状态：待 owner 确认。** 确认后并入 `product/requirements/core-beta.md`。

## Owner 的原始要求

> APP 应该支持访客登录。用户下载 APP 后可能不想注册，想进来看一眼。
> 我们产品设计得很棒，可以支持他以访客身份登录，看一下里面有什么功能。
> 等他觉得 OK 了，只要操作某些需要和数据库交互写数据的功能，就引导他注册。
> 付费功能可以放到后面再加。数据库要设计用户，还要有一个会员状态。

## 核心张力

这个产品的全部价值是**另一个真人回应你**。访客按定义是一个人、没有伴侣。所以：

- 访客**无法**体验核心闭环，因为闭环需要伴侣
- 如果**模拟**一个伴侣响应给访客看 → 直接违反红线 1 和 2（系统以伴侣口吻说话）
- 如果只给一个空壳 → 访客看不到任何值得注册的东西

**结论：访客模式不是错的，但必须围绕这个约束设计，而不是绕过它。**

## 决策 1 · 不叫「访客登录」，叫「产品预览」

访客**没有身份、没有 Dynamic、没有成员关系**。
把访客建模成 user 或 tier，会模糊隐私、同意与授权边界。

| 概念 | 归属 |
|---|---|
| 访客预览 | **客户端会话状态**，不是账号，不是 tier |
| account_state | pending / active / suspended / deleted |
| 邀请状态 | pending / accepted / declined / expired / revoked |
| 成员关系 | active / left / removed —— **仅在显式接受后开始** |
| 权益 entitlement | Core Beta 只有一个：`core_beta` |
| 关系角色 | Dynamic 内的可选配置，**永不是授权级别** |

**不要在有真实差异化权益之前发明 free / premium / guest 三档。**
访问权来自**活跃成员关系 + 对象可见性**，不来自商业档位。

## 决策 2 · 一份固定的虚构样例 Dynamic

预览全程使用**一份固定的、编辑审核过的虚构样例**。
访客可以浏览、可以推进叙述，但不能代任何虚构一方行动。

| 屏 | 访客能看到什么 |
|---|---|
| Today | 样例接收方视图：待办 / 已完成等待响应 / 已确认 / 已调整。可打开，**不能**完成或改期 |
| Attention | 真正需要另一方注意的东西。说明「在对方行动前什么都不会推进」 |
| Task Detail | 一个样例任务的完整历史：创建 → 完成 → 等待 → **人类显式确认** → 继续或调整 |
| Task List | 可浏览、排序、筛选。筛选状态设备本地临时保存 |
| Create Task | 展示字段与含义，用固定示例。**不接受个人自由文本**。「为你的 Dynamic 创建」→ 引导注册 |
| Acknowledgement Composer | 解释确认包含什么，展示一条**已发送的**样例。**没有可用的 Send 按钮** |
| Weekly Check-in | 一个双方各自独立提交的完整样例 + 一个等待第二方的样例 |
| Write Reflection | 展示虚构私密反思并解释可见性。**不接受访客输入** —— 反思从第一个字符起就是敏感的 |
| Us | 由双边事件构成的简短虚构历史。**不是**打分、streak 或排名 |
| Dynamic Overview | 解释成员关系、可见性、角色。明确「角色标签不授予同意或授权」 |
| Settings | 隐私说明、条款、年龄要求、数据处理、通知示例。设备级偏好（语言/无障碍）可用。关系与共享设置需要账号 |

## 决策 3 · 样例安全的七个条件

一份样例只有**同时**满足以下全部条件才是安全的，否则就是欺骗：

1. **持续标注**为虚构样例内容，而不是只在开头提示一次
2. 虚构的人类事件**归属到具名的样例人物**
3. **绝不**由访客的动作触发或生成伴侣响应
4. 叙述使用系统中性口吻与第三人称
5. 序列中**可见地包含「等待人类响应」状态**
6. 调整（Adjustment）被演示为**正常成功路径**，不是失败
7. 样例数据不可能被误认为访客自己的 Dynamic，也不可导入其中

**关键禁令**：访客不得按下「完成」然后立刻收到一个虚构的伴侣响应。
即使标注了样例，这个交互也在教授一个虚假承诺 ——
「系统会提供回应性的肯定」。这正是产品要反对的东西。

正确的做法是**叙述式状态浏览器**：访客选择「看看完成之后会发生什么」，
产品分步解释：一方记录完成 → 进入等待人类响应 → 稍后另一方**显式发出**确认 → 继续或调整。

> 预览要把**响应间隔本身**当作卖点：
> 「App 让这个时刻保持可见；**如何回应由你的伴侣决定。**」

## 决策 4 · 注册引导的边界不是「写数据库」

Owner 说「操作需要写数据库的功能就引导注册」。
**这个边界是错的** —— 它是实现细节，对敏感文本提示得太晚，对无害的设备偏好又提示得太早。

**正确边界：第一次表达真实的个人或关系意图。**

触发注册的具体时刻：

- 开始一个 Dynamic
- 邀请伴侣
- 从伴侣邀请链接继续
- 创建或保存一个真实任务
- **输入个人自由文本**（反思、check-in）—— 比「写数据库」更早
- 记录完成或请求调整
- 撰写或发送确认
- 配置共享 / 关系 / Dynamic 设置
- 打开与真实关系活动绑定的通知

提示文案要解释**为什么**需要注册：身份、隐私、成员关系校验、
送达给一个真实的伴侣 —— 而不是干巴巴一句「此功能需要账号」。

## 决策 5 · 访客绝对不能做的事

- 查看任何**真实**用户 / 邀请 / Dynamic / 任务 / 反思 / check-in / 确认数据
- 在完成认证邀请流程前，通过应用内敏感读取得知邀请人身份
- **接受或拒绝伴侣邀请**
- 成为 Dynamic 成员
- 创建、完成、调整、确认或共享任何真实对象
- 发送消息、通知、邀请或任何面向伴侣的事件
- 收到 AI 生成的赞美、惩罚、角色扮演或类伴侣响应
- 被放入发现、匹配、社区或任何公开界面
- 累积合规评分或模拟 streak
- 让样例动作被表述为同意
- 让角色选择被解释为同意或数据访问权

**访客不能接受邀请。** 必须先注册或登录 → 确认 18+ → 收到条款与隐私 →
审阅具体邀请 → **显式接受**。`REQ-JOIN-001` 与红线 6 都要求如此。

18+ 提示、条款、隐私、默认私密说明必须在**进入预览之前**出现。
注册时要**重复**法律所需的确认 —— 一次性的访客确认不构成账号级记录。

## 决策 6 · 访客状态不转换

**让访客根本无法创建敏感状态，就几乎没有东西需要转换。**

只带过去良性的设备本地状态：
- 语言与无障碍偏好
- 走完了哪些预览章节
- **一个安全的邀请 token** —— 仅为注册后能续上邀请流程
- 归因 / 来源元数据（视为系统级元数据）

**不带**：样例任务、样例确认、角色选择、个人草稿、反思、check-in、共享选择。

为什么转换在**这个**产品里格外危险：
- 用户可能不理解私下试验何时变成了存储的关系数据
- 样例事件与真实事件可能混淆
- Dynamic 存在之前创建的内容没有有效的共享/成员上下文
- 自动导入可能让内容意外暴露给伴侣
- 注册前的角色选择可能被误认为同意
- 在用户接受账号条款之前存储草稿，就已产生敏感数据义务

## 决策 7 · 最大风险

> **最大风险是让访客以为这是一个「单人 App，会生成关系性肯定」。**

一个打磨精良的模拟很容易暗示「我完成一件事，App 就像我伴侣一样回应我」。
那会吸引来**为错误产品而来的用户**，违反人类响应原则，
并让真实的双人体验显得更慢、像坏了。

缓解方式 —— 把**响应间隔**做成预览的主角：
- 完成与确认永远是两个独立事件
- 永远包含「等待人类响应」状态
- 确认归属到虚构的**人**
- 绝不由访客动作生成响应
- 调整与完成并列演示
- 早早说明：产品通过**两个知情成年人共享的 Dynamic** 才真正运转
- **访客成功的度量是理解与合格意向**（开始注册、打开合法邀请、选择邀请伴侣），
  **不是**模拟任务参与度

## 我（Claude）与 Codex 意见不同的一处

Codex 主张「Create Task 不接受任何个人自由文本」。
我认为这一条**在 Create Task 上过严了**。

理由：Create Task 的字段（标题、时间）在没有 Dynamic、没有收件人的情况下
**本身不是关系数据**，它就是一句话。禁止输入会让预览变成一堆只读说明卡，
恰好落进 owner 要避免的「空壳」问题。

我的建议：**允许在 Create Task 里输入，但输入停留在设备内存、永不落库、
永不导入**，并在用户点「保存 / 指派」的那一刻引导注册 —— 那才是真实关系意图。

**反思（Write Reflection）与 check-in 则完全同意 Codex：从第一个字符起就拒绝。**
反思在这个产品里天然是私密敏感内容，性质与一句任务标题不同。

**这一条需要你裁定。**

## 数据库影响（重要）

现有 schema 有三处**硬约束**会挡住任何「访客也建一条 user 记录」的做法：

```sql
users.email  text NOT NULL
CONSTRAINT users_email_not_blank_ck CHECK (btrim(email) <> '')
CREATE UNIQUE INDEX users_normalized_email_uq ON users ((lower(btrim(email))));
```

同时有 **10 处外键** `REFERENCES users(id)`（memberships / invites /
expectations / occurrences / acknowledgements / adjustments / audit）。

**这正好印证了「访客不该是一条 user 记录」的结论** —— schema 已经在
用约束表达「用户必须有真实身份」。给访客造一条空 email 的 user，
要么放宽 NOT NULL（削弱所有既有保证），要么塞一个假邮箱（污染唯一索引）。
两者都是在为一个不该存在的实体让路。

**所以访客零 schema 改动。** 需要的迁移只有一条，且与访客无关：

```sql
-- V10：权益。与访客无关，是为「会员状态」这个要求准备的骨架。
ALTER TABLE users ADD COLUMN entitlement text NOT NULL DEFAULT 'core_beta';
ALTER TABLE users ADD CONSTRAINT users_entitlement_ck
    CHECK (entitlement IN ('core_beta'));
```

单值枚举是**故意**的：付费档位未定义之前，先占好列的位置，
但不让休眠的定价概念影响当前行为。将来加档位只需放宽 CHECK。
