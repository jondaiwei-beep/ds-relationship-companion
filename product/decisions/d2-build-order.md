# D2 · 建屏顺序与门禁开放顺序

Written 2026-08-29。自我决策，经 Codex 评审后修正。

## 决定

**Sprint 1 不需要任何门禁** —— 路由、会话、认证守卫、导航提升、真 `main.dart`
都不是新屏。但它**仍然需要显式的安全与导航验收标准**：认证守卫、深链、
会话过期、路由恢复，这些不引入新屏也能违反可见性规则。

## 顺序（已按 Codex 意见修正）

我最初的顺序是：入口 → 激活(31/07/08/12) → 邀请(09/10/11) → 闭环。
**这个顺序有一个同意缺陷**：把角色、结构、节奏放在邀请之前，
等于让一个人在伴侣同意之前就配置了一个「共享的」Dynamic 并给对方指派了角色。
直接违反红线 6 —— **邀请不得静默授予同意**。

**修正后的顺序：**

```
入口 → 最小个人设置 → 邀请 / 加入 → 双方同意 → 共享激活 → 闭环
```

分成两条路径，而不是一条：

| 角色 | 路径 |
|---|---|
| 邀请方 | 账号 → **个人**最小设置 → 准备并发送邀请 |
| 被邀方 | 邀请落地页 → 账号/登录 → 理解提议 → **显式同意** |
| 双方 | **同意之后**才配置或确认共享的角色、结构与节奏 |

**任何在接受之前配置的东西，必须明确标注为「私人提议 / 草稿」，
且被邀请方必须能够拒绝或修改。邀请本身绝不创建一个双方活跃的 Dynamic。**

## 门禁开放批次

| 批次 | 屏 | 说明 |
|---|---|---|
| 1 | SCR-04 / 05 / 06 | 入口、登录、注册。不进门什么都够不着 |
| 2 | SCR-31 / 07 | 目标、角色 —— **仅作为个人偏好**，不是共享配置 |
| 3 | SCR-09 / 10 / 11 | 邀请、Web 加入、双方同意。一期风险最高 |
| 4 | SCR-08 / 12 | 结构、起始节奏 —— **移到同意之后**（原本在批次 2） |
| 5 | SCR-02 / 33 / 03 / 32 | 完成→等待、确认编辑器、收到确认、Attention |

## 为什么不先建 SCR-33

早先的计划建议第二个就建 SCR-33 确认编辑器，理由是「核心红线住在那里」。
**我否决了这个建议**：一个没有登录、没有伴侣、没有 occurrence 的编辑器
无法被走通也无法被验证 —— 那会是第一个不可达屏旁边的第二个不可达屏。

Codex 同意这个否决，但补了一条我没想到的：
**不要因此推迟 SCR-33 的风险。** 提前开它的对齐工作，
并用一个小的测试夹具/原型覆盖这些行为：

- 完成永不创建、也永不在视觉上暗示确认
- 起草不创建任何东西
- 只有显式的人类 Send 才创建确认
- 编辑器**永不预填**以伴侣口吻呈现的语言
- 发送、重试、重复点击、离线恢复、失败态都不能产生歧义确认

然后等一条真实的端到端 occurrence 存在时，再实现真屏。

## 交付方式的警告（Codex，已采纳）

> **不要先做完十一个打磨精良的前置屏再去碰闭环。**
> 先打一条粗糙的、贯穿「入口 → 邀请 → 同意 → occurrence → 完成 → 确认」
> 的 walking skeleton，然后再逐屏加深状态族。

这条改变了一期的执行方式：Sprint 2-5 不是「一个 Sprint 交付一批完成态的屏」，
而是**先贯通再加深**。
